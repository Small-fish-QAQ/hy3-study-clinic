历史 prepare 已被 Runner 领取，provider 为 `moma`、模型为 `glm-5.3`，预算预检通过并发出了 HTTP 请求。不存在未调度或 Fake 冒用的证据。历史首个可确认失败在完整结果返回前；原非流式记录没有响应头，不能据此证明未调用或零计费。

本轮真实探针进一步区分连接与生成：连接只需返回 `{"ok":true}`，约 3.5 秒；原 3 块提取约 **213.6 秒**，19,743 输出 Token 中上游报告 18,486 reasoning。流式试验约0.6秒就收到响应头，失败的15块请求在240秒内仍收到3,091个事件和36.8KB推理数据；一份异常 review 甚至消耗22,490输出Token却没有可见正文。可确认的是 **默认深推理与过重工作包无法稳定产生期限内的完整正文**，而不是客户端没有发请求。不能把原历史超时的全部网关原因推断成已知。

修复落在实际链路：

- `completionResponse.ts` 严格聚合 SSE，处理 UTF-8 / CRLF 分片；立即丢弃推理文本，只保留计数。要求正常 finish 与 `[DONE]`，保存用量及 request ID；截断流不能发布。
- `courseProvider.ts` 共用真实 HTTP 预算，按实际可见正文与时延调节工作包。MoMA / glm-5.3 的提取/规划/题目作者使用 `reasoning_effort=low`，独立核查/正文/答疑/判分使用 high。相同小请求 default 约37.9秒、low约10.8秒，后者报告1 reasoning Token；题目作者低推理也已真实验证，这是本配置端点实测行为，官方GLM文档未列该参数。改变题目作者请求仅更新该方法的缓存身份，已成功盲解和 rubric 核查仍可复用；显式推理配置保持优先级。
- `knowledgeWire.ts` 使用包内短来源 ID 和知识数组下标，服务器恢复原精确 block ID / 跨度，不让模型逐字计算坐标或复制长ID。原公共合同和数据库身份未改变。
- `courseKnowledge.ts` 将表格、公式、证明和邻接条件作为完整单元，处理成功包后重算剩余包；有效成果保留，密集规则表的输出估算增补。没有截断来源、固定知识上限或自动无限重试。
- `coursePlanning.ts` 先应用选定深度及蓝图同步，再校验最终候选；可选领域的目标不误当成必考门。完整原 map 经 hash / 实际 provider / 物理调用出处核对后重新校验和真实必要 review，避免第三次购买整份规划。原拒绝历史保留。
