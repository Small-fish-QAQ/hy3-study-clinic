## 1. 一句话概述

**Hy3 Study Clinic 是一个基于 Hy3 的学习执行 Agent：学习者交付自己的课程资料与学习目标，
Hy3 负责全部开放式的教学语义工作，确定性本地代码保留全部状态权威，任何"你已掌握"的结论都
必须能回溯到判据门控的正式证据与资料中的确切出处。**

在此之上，本项目把「如何评价一个没有唯一标准答案的学习 Agent」当作**与应用同等重要的第二
个交付物**：定义可操作的评估维度，发布半自动评测方法规格，并将在终稿前实现评测器与实验，
验证**这套评估方法本身是否可靠**。

## 2. 目标用户与真实问题

### 2.1 目标用户

- 用课件、教材、PDF、技术文档、源码进行系统学习的大学生与研究生；
- 需要在数天到数周内吃透一门课、一个技术主题或一个项目知识域的自学者；
- 希望获得讲解、练习、反馈与复习安排，但**不愿意把「学没学会」的判断完全交给模型主观感觉**
  的学习者。

### 2.2 用户真正卡住的地方

通用大模型已经很擅长「就地解释一个概念」。真实的持续学习是另一回事，它以很具体的方式失败：

| 失败模式 | 学习者的实际体验 |
|---|---|
| **学习路线漂移** | 对话越长，越偏离最初的目标、范围与节奏；第 5 天已经不知道自己在学什么 |
| **资料事实与模型扩展混淆** | 模型合理地补充了通用知识，然后以「你的资料里写了」的口气讲出来 |
| **证据错绑** | 结论本身正确，但引用指向了错误的段落——比完全讲错更难发现 |
| **虚假掌握** | 熟悉的题、熟悉的表述都对；换一种表达、两周之后、迁移到新场景就崩 |
| **状态不可复核** | 聊天记录无法回答「系统凭哪次正式证据认为我掌握了这一点」 |

Study Clinic 针对的是最后一个问题。它的设计目标不是「回答得更好」，而是
**让关于学习状态的每一个有后果的结论都可被复核**。

### 2.3 为什么必须引入大模型（为什么是 Hy3）

学习执行链路中有一批工作**无法仅靠规则可靠实现**：

- 从一份任意结构的资料中判断「哪些是概念、概念之间是什么依赖关系」；
- 把资料切分成有教学意义的学习单元与学习目标——切法不唯一，但有好坏；
- 针对一个具体学习目标写出讲得清楚的解释、例子与类比；
- 判断一段简答是否命中了评分要点——学生的措辞与参考答案几乎从不相同；
- 判断一条候选证据与一个学习目标命题之间是**支持 / 无关 / 矛盾**；
- 从错误表现反推「他到底缺了哪一块」，并提出针对性的补救。

这些都是**开放式语义判断**，没有唯一标准答案，规则、检索与模板单独无法可靠完成。这正是引入
Hy3 的必要性——Hy3 不是本项目的一个文本生成接口，而是承担了系统中**无法仅靠确定性规则可靠
完成的那一层**。

同时必须说清反面：上述工作**没有一项**可以直接决定学习记录。这也是本项目的核心工程主张。

## 3. Hy3 做什么，确定性代码做什么

### 3.1 Hy3 承担的语义工作（均已在代码中实现）

| 类别 | Hy3 的具体职责 |
|---|---|
| 课程构建 | 概念抽取（分节、增量）；Curriculum / LearningUnit / 学习目标提案；StudyPlan 与后继计划提案；跨文档概念对齐提案 |
| 教学 | Teaching Brief 讲解槽位生成（组合式）；Practice 命题（在 Lesson 通过全部门控之后的**独立一次调用**）；Tutor 在受控动作词表内选择教学动作 |
| 语义判断 | 简答语义评分与评分要点覆盖；**盲态 source-dependency 归因**；**候选证据关系分类**（`relevant / unrelated / contradicts_claim`）；**有界组合式 support group 提案**（最多 4 组，每组 1..5 条证据） |
| 诊断与补救 | 误解假设；针对性 Repair 提案；对抗性掌握挑战候选题（开发/审计通道） |

### 3.2 确定性本地代码保留的权威

逐字引用与偏移量校验、页/节/幻灯片/DOM 定位、不可变资料修订；ID、关系词表、环检测、schema
校验、版本血缘与 fingerprint；**证据覆盖（coverage）、绑定匹配（bindingMatch）、错绑
（misBinding）、矛盾（contradiction）、构念有效性与最终 verdict**；客观题答案与分数算术；
判据门控的 Formal Evidence；进度对账；掌握状态；FSRS 复习调度；租约与陈旧请求围栏、幂等、
预算、持久化与权限。

### 3.3 两条边界（本项目最值得说的部分）

**（1）Hy3 从不给出最终裁决。**

在证据支撑判定中，Hy3 只输出「每条候选证据与命题的关系」和「哪些证据组合起来足以支撑命题」。
`coverage / bindingMatch / misBinding / contradiction / verdict` 全部由本地代码从**模型看
不到的私有绑定集合**计算。更关键的是：持久化的 verdict 在**每一个有后果的下游边界都会被重新
推导并比对**，不一致即报 `semantic_local_verdict_mismatch`。这意味着——即使有人硬塞一个模型
裁决进去，它也无法通过接纳、StudyPlan、路线激活与 Lesson 前置门控。

**（2）Hy3 看不到当前绑定了哪条证据。**

提供给模型的输入在「私有绑定不同、候选证据全集相同」的两种情况下**逐字节相同**（有三处回归
测试对此做断言）。模型因此无法为一个它观察不到的选择自证合理。

这条设计换来一个具体能力：**「结论正确但绑到了错误段落」从一个自证正确的盲区，变成一个可检
测、可确定性重绑的状态。** 这是纯对话范式通常缺少的结构化能力。

### 3.4 学习闭环

```text
学习者资料  ->  不可变修订 + 精确 SourceBlock
                     |
          Learning Contract        目标 / 深度 / 时间——学习者确认
                     |
              Curriculum           Hy3 提案 -> 本地门控校验 -> 学习者接纳
                     |
               StudyPlan           版本化、已接纳的路线
                     |
            SessionAgenda          现在该做什么
                     |
      Lesson -> Practice -> Tutor  教学环节，全部 credit: none
                     |
           Formal Assessment       唯一的计入路径
                     |
    判据门控 Formal Evidence  ->  进度对账
                     |
        掌握状态  /  Repair  /  复习调度
```

Formal Assessment 之上的一切都**不计入**：对话、非正式自测、「我看懂了」都不会改动学习记录。
之下的一切是确定性、版本化、可审计的。

## 4. 为什么这个场景「不存在唯一标准答案」

这不是修辞，而是本任务成立的前提。以同一份《认知负荷》讲义为例：

- **课程切分**：切成 3 个学习单元还是 6 个？先讲工作记忆还是先讲负荷类型？都有合理版本。
- **讲解**：用双通道模型讲、用带宽类比讲、用一个具体的课堂例子讲——都可能是好讲解。
- **命题**：考「说出三种负荷类型」和考「判断这个教学设计增加了哪一类负荷」考的是不同能力，
  哪个更该考取决于学习契约的深度要求。
- **评分**：学生写「脑子一次装不下太多东西」是否命中了「工作记忆容量有限」这个要点？可辩护，
  但不唯一。
- **诊断与补救**：同一次做错可以归因为概念不清、迁移不足或读题失误，对应完全不同的补救。

因此「答案正确率」无法评价这个系统。必须自定义一套评估方法，并且——必须证明这套方法本身可靠。

## 6. 评估体系设计（StudyEval v1）

### 6.1 首先要区分的两层——这是本方案最关键的一个界定

竞赛要求的是**面向开放式 AI 应用的完整评估方法**。它**不等于**产品内部的运行时语义门控。
两者互相印证，但不是一回事，本方案严格分开报告：

| | Layer A：产品内运行时保护 | Layer B：StudyEval 竞赛评估器 |
|---|---|---|
| 回答的问题 | 系统**拒绝**做什么 | Hy3 的教学产出**好不好** |
| 内容 | schema 校验、逐字 provenance、盲态 support group 验证、判据门控、版本与陈旧围栏、预算 | 7 个维度对**冻结的真实 Hy3 输出**打分 |
| 状态 | **已实现** | **本方案设计，终稿前完成** |
| 报告方式 | 「保护机制表」 | 应用质量表 + 评估器有效性表 |

把 Layer A 当成竞赛评估结果来报告，等于把「状态安全」冒充「教学质量」。本方案不这么做。

### 6.2 评估单元与任务族

**评估用例（Evaluation Case）** = `{caseId, 任务族, 冻结输入上下文, 冻结 Hy3 产出,
质量档位, 构造来源与变异日志, 各维度 gold 标签, 目标维度}`。

六个任务族，全部对应真实 Hy3 操作：

F1 Curriculum 提案 ｜ F2 Teaching Brief 讲解 ｜ F3 Practice 命题 ｜
F4 简答语义评分 ｜ F5 证据关系与 support group ｜ F6 Repair 提案

### 6.3 七个评估维度（每个维度三档成文锚点）

覆盖 5 个以上关键维度的官方要求由此满足。**不为凑数量而扩维**——每个维度都必须对应一个真实
的 Hy3 产出，并且能写出**让不同评审依据同一操作标准尽可能收敛**的判定条件。

| ID | 维度 | 评的是哪个产出 | 打分方式 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|---|---|---|
| **D1** | 来源事实一致性 | F1,F2,F4,F5 | 确定性 + 结构化语义 | 每条 source-specific 断言都有精确可验证跨度，且与已接纳资料无矛盾 | 至少一条无法验证，但没有矛盾 | 至少一条与资料矛盾，或存在伪造引用 |
| **D2** | 证据绑定正确性 | F5（含 F2 引用） | **纯确定性** | 当前绑定中存在能完整支撑命题的 support group | 资料中存在可支撑组合，但当前绑定错误（错绑） | 不存在可支撑组合，或已绑定证据与命题矛盾 |
| **D3** | 目标与范围保真度 | F1,F2,F3 | 确定性 + 语义 | 内容在已接纳范围内且符合契约构念深度；扩展知识被显式标注为通用 | 在范围内但深度失配，或存在未标注的通用扩展 | 超出已接纳范围，或把通用扩展当作资料事实断言 |
| **D4** | 教学正确性与可理解性 | F2,F6 | **语义 + 人工** | 无错误陈述、无关键跳步、例子服务于目标、关键术语先定义后使用 | 结论正确但存在 ≥1 处跳步或 ≥1 个未定义关键术语 | 存在 ≥1 处教学性实质错误，或循环解释/不可用 |
| **D5** | 评估可辩护性 | F3,F4 | 确定性 + 语义 | 前提可见、答案未泄漏、判据可由资料辩护、评分与自身证据一致 | 可作答但存在未绑定评分点或局部歧义 | 不可作答、答案泄漏、琐碎复述，或评分与自身证据矛盾 |
| **D6** | 诊断针对性与补救有效性 | F6 | 确定性（种入缺陷）+ 语义 | 命中真实缺口并给出针对该缺口的具体动作 | 领域正确但只是泛化重讲 | 诊断错了缺口，或补救不可执行 |
| **D7** | 虚假掌握抵抗（**系统级**） | 场景回放 | **纯确定性** | 换表述 / 延迟 / 迁移失败后不产生持久掌握 | 掌握保留但被标记为风险 | 仅凭熟悉表述通过即断言持久掌握 |

**从 v0 剔除的两个维度**：「证据完整性」与「工作流可靠性」。它们衡量的是**产品运行时保护**，
属于 Layer A，单独作为保护机制表报告——把它们计入应用质量维度会虚增维度数，并把状态安全冒充
教学质量。另外把「公平性/可作答性」并入 D5、「可执行性」并入 D4，以换取一组内聚的维度而不是
一张长清单。

### 6.4 Hy3 评 Hy3 的循环性控制

这是 LLM-as-judge 方案最容易被质疑的地方，本方案用六条控制回应：

1. **判官只输出观察，不输出分数。** 语义判官发出的是原子结构化观察
   `{缺陷类型, 位置, 引用片段}`，档位由本地规则推导。
   ——这**刻意复用了产品自身的权威模式**：模型观察，本地裁决。同一个思想从产品迁移到评估器，
   是本项目一致的架构主张，而不是临时补丁。
2. **判官盲态**：看不到质量档位、变异日志、生成侧的理由。
3. **独立 prompt 身份与 schema 版本**，与任何生成 prompt 分离。
4. **同时报告两个基线打分器**：仅按长度打分、仅按确定性规则打分。语义层必须同时优于两者，
   否则「语义层带来了增量信号」这个论断不成立。
5. **人工标注只用于校准判官**，判官从不自我校验。
6. **D2 与 D7 完全不调用模型**——本框架最锋利的两个论断因此与模型无关。

## 7. 评测样本集设计

### 7.1 规模与构成（共 86 个评估单元）

| 组别 | 数量 | 构造方式 |
|---|---|---|
| 好 / 中 / 差三元组 | 18 组 = **54** 个（6 个任务族 × 3 组） | **好档 = 真实 REAL_HY3 输出**，通过全部门控并经作者复核；中/差档 = 对好档做**脚本化确定性变异**，保留变异日志 → gold 标签由构造方式直接给出 |
| 自然采集的差档 | **≥6**（属于上面 18 个差档的子集） | 取自私有报告中已记录的**真实 REAL_HY3 失败**，标注为自然样本而非人工变异 |
| 对抗样本 | **20**（5 类 × 4） | A1 无效加长 ｜ A2 术语堆砌 ｜ A3 伪造引用 ｜ A4 结论正确但绑定错误 ｜ A5 熟悉表述制造假掌握 |
| D7 系统级场景 | **12** | 换表述、延迟、迁移、近邻混淆——在真实状态机上回放 |
| **合计** | **86** | 反例 + 对抗 = **38 / 86 ≈ 44 %** |
| 人工标注子集 | **30**（跨任务族与档位分层抽取） | 单一标注者（作者本人） |
| 重复自动评测 | **30 × 3 轮** | 稳定性 |

资料来源：4 份真实课程文档（2 中文、2 英文/双语）+ 仓库现有 5 份 fixture；至少覆盖两个不同学科，
避免单领域过拟合。

### 7.2 为什么是 86 而不是 60–100

这个数字来自**产能推算，而不是野心**：距终稿 15 天、单人、每个 case 完整标注约 6–10 分钟，
另需承担真实 Hy3 生成成本与评估器实现工时。**30 个有完整 gold 溯源的严格标注样本，比 100 个
浅标注样本更有证据力。** 若进度落后，收缩顺序为：先减 D7 场景（12→8）并明示，绝不缩减人工标注
质量或对抗样本。

### 7.3 关键方法论说明

「好档必须是真实 Hy3 输出」这一条是本次相对早期内部版本最重要的修正。早期私有版本 v0 的
24 个样本全部是**人工编写的 fixture**（实跑提供方调用数为 0），其排序准确率因此**接近同义反复**
——作者既写了样本又写了标签。竞赛要求评的是**AI 应用的产出**，所以本次每个三元组的好档都必须
来自真实模型。

## 8. 评估流程实现

半自动、分层，可离线复跑：

1. **冻结**：语料在任何评估运行之前冻结并计算 corpus hash，结果无法回头改写样本；
2. **确定性检查**：能被规则客观判定的属性绝不交给模型（引用存在性与偏移、绑定集合运算、
   答案泄漏、前提可见性、状态变更为零）；
3. **结构化语义观察**：仅开放式属性交给 Hy3 判官，输出原子观察；
4. **本地聚合**：由规则从观察推导各维度档位与 case 级判定；
5. **基线对照**：同一批样本再跑「仅长度」「仅确定性」两个基线；
6. **人工标注**：分层子集独立标注，用于校准判官；
7. **重复运行**：30 个样本 ×3 轮，记录档位稳定性与判定翻转率。

**选择这一实现方式的依据**：完全靠规则无法评价讲解质量；完全靠 LLM 总分则无法复核、易被篇幅
与术语欺骗、且构成自我循环。分层方案让每个属性由最合适的机制判定，并把模型的作用限制在「它
真正不可替代」的那一段。

### 8.1 运行模型与命令接口（确定性与模型调用分离）

StudyEval 的确定性部分与语义部分在**运行时严格分离**，只需两个命令：

| 命令 | 是否需要凭据 | 职责 |
|---|---|---|
| `studyeval:offline` | **不需要** | 语料 schema 校验与 corpus hash 核对；D2、D7 两个纯确定性维度；确定性检查；**从已冻结的语义观察**推导档位与聚合；两个基线打分器；生成结果表 |
| `studyeval:hy3` | **需要显式 Hy3 凭据** | 唯一的语义判官通道：对开放式维度产出原子结构化观察，并把观察**冻结写入语料** |

由此得到的性质：

- **语义观察一次采集、多次离线复算。** 观察被冻结后，档位推导、聚合、基线对照与结果表生成全部
  离线可复跑且结果可复现——评审者无需任何凭据即可复核推导过程。
- **重复评测的含义被明确定义**：第 9.2 节的「重复自动评测 ×3 轮」指**重复采集语义观察**
  （`studyeval:hy3` 跑 3 轮，每轮独立冻结），用于度量模型判断的稳定性；离线聚合本身是确定性的，
  重复它只能验证实现无随机性，不构成一致性证据。
- 因此在本项目中，**接触真实模型的命令共两个**：`eval:hy3`（既有结构化适配器评测）与
  `studyeval:hy3`（语义判官）。其余全部离线。
- 所有 StudyEval 运行强制 `VISUAL_PROVIDER=disabled`。

**当前状态：以上命令与语料尚未实现。** 本节是终稿前要交付的规格，实现排期见第 12 节。
私有的 v0 评估器（8 维度、24 个 fixture 样本、可执行离线 runner）是**前期方法论工作的证据**，
不是最终公开的 StudyEval 实现，也不会被当作 StudyEval 的结果来报告。

## 9. 评估方法的有效性验证

**本节回答的是「我们的评估器可不可靠」，而不是「Study Clinic 表现好不好」。** 这两件事在结果
呈现上也严格分开（见第 10 节）。

### 9.1 判别力验证（官方必做项一）

- 18 个三元组 → **严格三元排序准确率**（good > mid > bad 全部成立的比例）；
- 54 个成对比较 → **成对排序准确率**；
- 每个维度的 **Kendall tau-b**（三档序数、必然大量并列，tau-b 是处理并列的正确选择；
  **不使用** 三点 Spearman）；
- 3×3 档位混淆矩阵；
- **每一个排序失败都做归因**并写入报告。

### 9.2 一致性验证（官方必做项二）

- 30 个人工标注样本 → 与自动结果的**完全一致率**、**相邻一致率（±1）**；
- 其中 20 个样本在**间隔 ≥24 小时后重标** → **标注者自身一致性（intra-rater）**；
- **重复采集语义观察 3 轮**（`studyeval:hy3` 独立跑 3 轮并分别冻结）→ **众数档位稳定率**与
  **判定翻转率**。

**每个维度单独报告适用样本量 `n`，不假设七个维度都是 n=30。** 一个样本只在其**目标维度**上有
可用标签：F5 任务族的样本不为 D4 提供标签，讲解类样本不为 D2 提供标签。预期的适用规模差异很大，
其中：

- **D7 是系统级维度，其 `n` 最多等于计划中的系统场景数（12，若进度收缩则为 8）**，且这些场景
  不参与 D1–D6 的统计；
- D2 与 D7 为纯确定性维度，其一致性问题是「人工是否同意确定性判定」，与语义判官的一致性不是
  同一件事，将分开列出。

**加权 kappa 的使用条件**：仅对**标签结构适用且 `n` 可辩护**的维度计算二次加权 kappa（QWK），
并同时给出该维度的 `n`。对于适用样本量过小的维度，**只报告完全一致率与相邻一致率**，并明确写出
「该维度样本量不足以支撑 kappa 类统计量」，而不是给出一个不可靠的系数。

**必须诚实声明的一点：本项目只有一名标注者，因此在数学上无法计算标注者间一致性
（inter-annotator agreement）。** 报告将给出「人工 vs 评估器」的一致性（这是评审者与仪器之间的
一致性，成立）与标注者自身一致性，并明确说明缺少第二名标注者是本次验证的局限。
**不会**为了指标看起来学术而使用暗示两名评审的 Cohen's kappa，也不使用 Krippendorff alpha 与
ICC——它们与本次的标签结构不匹配。本节不再引入任何额外统计量。

### 9.3 对抗性验证（官方鼓励项）

20 个对抗样本，五类攻击：无效加长、术语堆砌、伪造引用、结论正确但证据绑定错误、熟悉表述制造
假掌握。度量：

- **false-pass rate**：对抗样本被判为「可接受」及以上的比例；
- **分数虚高幅度**：对抗样本相对其干净对照的分差；
- **篇幅混淆检查**：干净样本上 token 长度与总分的 Kendall tau，应接近 0。

**false-pass 的定义在实验前写定**：任一 case 在其目标维度上未落到应有的低档位，即计为
false pass。不允许事后调整判定线。

## 10. 结果呈现：应用质量 与 评估器有效性 分开报告

终稿将输出两张**结构上分离**的结果表。

**表一 · 应用质量**：在真实 Hy3「好档」产出上，各维度档位分布；按 reason code 的失败模式归因；
按任务族拆分。回答的是「Hy3 在这个真实学习应用里表现如何、在哪里开始不可靠」。

**表二 · 评估器有效性**：三元/成对排序准确率、各维度 Kendall tau-b、人工一致率与 QWK、
标注者自身一致性、重复运行稳定性、对抗 false-pass rate、篇幅混淆系数、两个基线的对照结果。
回答的是「我们这套评估方法本身站得住吗」。

另附 6–10 个典型 case 归因，**其中至少两个是评估器自己判错的样本**。报告会同时给出达到预期与
未达预期的结果——只展示成功案例的一致性报告没有信息量。

## 11. 失败模式与能力边界

本项目对能力边界的表述是产品的一部分，不是免责声明：

- **逐字引用校验证明的是「位置」，不是完整语义蕴含。** 代码、UI 与文档统一保持这个区分。
- 目标支撑评估器是**模型辅助**的，可以判错；结构化观察、冻结权威、本地构念规则与下游重复校验
  使它**可审计且失败即关闭**，而不是形式化证明。
- 掌握与复习调度是**透明的本地启发式**，不是经过校准的认知诊断；误解在有评分证据之前始终是
  假设。
- 讲解可以超出上传文本，但这些段落被显式标注为 AI 讲解，永不作为评分证据，其事实质量取决于
  所配置的模型。
- PDF 导入依赖内嵌文本层，**无 OCR**；复杂多栏、旋转文本、图内文字不做重建。
- 离线 Fake 评测验证结构与安全边界，**不验证教学质量**；真实提供方样本小且依赖模型与 API，
  属指示性结果而非 benchmark。
- 可选的视觉描述通道默认**关闭**，输出仅为建议性，永不进入正式证据、评分、掌握或任何权威，
  也不参与本次评测。
- **本项目未做学习效果研究，不对教育有效性作任何断言。**

已观察到的 Hy3 典型失败模式（将在终稿按频次可得与不可得分别标注）：在证据充分时倾向于过度扩展
通用知识；在候选证据近邻相似时关系分类不稳；在需要多证据联合时偏向给出单证据组；对深度要求的
构念层级把握不稳。这些正是 D1/D3/D5 与 support group 机制要抓的东西。

## 15. 结语

本项目想回答的不是「大模型能不能教人」，而是：

> **当 Hy3 真正进入一段长期、开放式、没有唯一标准答案的学习过程之后，它的教学行为能不能被
> 验证、错误能不能被定位、证据能不能被追溯、学习状态能不能被信任——以及，我们用来判断这一切
> 的那把尺子，本身可不可靠？**

因此本项目同时建设**应用**与**评估体系**，并且在两者中使用同一个架构主张：

**模型负责观察与生成，本地代码负责裁决。** 在产品里，这条主张让「结论正确但绑定错误」变成可
检测的状态；在评估器里，同一条主张让判官只输出可复核的原子观察，而不是一个无法追问的总分。

一个只会运行的 Demo 不足以说明问题。本项目希望交付的是一个能回答**「这次教学为什么值得信任、
哪里出了问题、模型的能力边界在哪里、以及我们凭什么这么判断」**的 Hy3 学习应用。
