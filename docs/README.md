## 为什么仓库里还有其他 Markdown

有些 Markdown 是程序输入或实验原件，也有些记录需要保留原来的路径。它们各有用途，首次阅读无需遍历。

| 位置                                                                                                                       | 保留原因                                                                     |
| -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| [eval](../eval/README.md) 中的方法、协议、分析与目录说明                                                                   | 与原始数据一起记录实验如何进行、结果怎样复算；受完整性校验保护的文件保留原文 |
| [eval/fixtures](../eval/fixtures)                                                                                          | 五份供程序读取的测试材料，Markdown 在这里是数据格式                          |
| [docs/history](history)                                                                                                    | 旧评估报告、人类标注分析及三份发布审计，统一由历史索引引导                   |
| [早期真实调用报告](evidence/hy3-online-verification.md)                                                                    | 与同目录 JSON 由脚本一起生成，测试检查两者严格对应                           |
| [字体](../apps/web/public/fonts/README.md)与[图标](../apps/web/public/icons/tabler/README.md)说明                          | 随资源保留来源、授权和使用要求                                               |
| [EVALUATION.md](EVALUATION.md)、[EVALUATION_RESULTS.md](EVALUATION_RESULTS.md)、[HUMAN_VALIDATION.md](HUMAN_VALIDATION.md) | 三个旧路径入口，只指向当前报告或历史正文，不再维护另一套说明                 |

最后三个入口服务于 2026-09-12 证据包中的旧链接。该证据包连 README 都保存了文件哈希，直接改写会使原包的校验失败；保留短入口可以同时维持原文件和链接可用。

## 文档维护约定

**每个主题只维护一处完整说明。** 产品问题、设计理由和评估解释写进主报告；实现细节写进架构；安装与配置写进运行指南；检查命令写进验证指南。首页只作简短介绍和引导。

新增能力先更新对应章节，不为每次迭代再写一份总结。只有出现现有页面无法承载的独立用途时，才新增文档。旧结论和一次性发布审计进入历史目录。

解释设计时，先说遇到什么具体问题，再说选择及代价。面向初次阅读者，用“题目、作答、通过记录”等具体词；必要术语首次出现时解释。版本哈希、调用统计和运行编号放到复现部分或附录。

统计值交代对象、分母和限制，区分人类评分、模型判断与助手复核。模型实际输出和历史原文作为引用保留，不为润色而改写。冻结协议、样本、标签和结果不能通过文档整理重新修改。

合并或迁移时，同步检查文件路径和标题锚点。当前文档的格式与检查步骤见[验证指南](VERIFICATION.md#文档检查)。
